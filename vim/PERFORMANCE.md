# 搜索终端偶发替代字符（2026-10-03）

用户截图中，左侧旧光标位置和 `已安装` 出现 `�`，右侧中文正常。
对应文件和搜索后端的输出均为有效 UTF-8，没有 U+FFFD。实际复现来自本机
Vim 9.1.1752 内置终端：将 `prefix 中文` 拆成三个 PTY 输出片段后得到 `prefix ��文`；
先发送 `ESC ( B` 再执行相同写入，得到完整的 `prefix 中文`。

libvterm 初始的 G0 和专用 UTF-8 解码器各自维护状态，
[解码器选择](https://github.com/vim/vim/blob/v9.1.1752/src/libvterm/src/state.c#L295)
依赖本次片段的首字节。ASCII 开头的片段在中文字符中途结束后，下个片段可能换到
另一个解码器，因此连续的有效 UTF-8 字节被显示成替代字符。
搜索 helper 的 `run` 入口向终端 stderr 发送一次三字节 `ESC ( B`，将 G0 指定为 ASCII，
让非 ASCII 字节始终走同一个 UTF-8 解码器。文件、最近文件和文本搜索共用此初始化；
结果仍通过原有 stdout 协议传递。新增开销只有一次 shell 内置 printf，没有增加进程。

- **新建/重命名保护已有特殊文件。** 原先的 `filereadable()`/`isdirectory()` 检查
  漏掉失效符号链接：新建会穿过链接创建其目标，重命名会替换链接。
  现在统一检查 `getftype()`；失效链接及 FIFO 的回归验证原对象和源文件保留。
  这是已有目标检查的修复，不是针对所有并发文件系统变化的事务保证。
- **扩展 netrw v184 的加速适配。** 新列举入口返回列表，减少重复路径拼接和属性读取；
  树渲染批量写入连续叶子，并使用 v184 的链接子树缓存键。
  仅接受已核对完整函数体的 SHA-256；未知实现继续使用原生代码。
  长列表、大小/时间排序、动态列宽等场景仍使用原生列举。
- **增加 `<leader>w` 保存全部文件。** 普通/可视模式可用，避免终端流控拦截 `Ctrl-s`；
  可视模式保存后恢复选区。
- **补齐与修正测量。** 新增 `tests/startup_latency.py`；编辑器基准加入首页、帮助、
  quickfix 的开关。注释基准读取实际 `commentstring`，支持本机默认的 `//`。
  测试/搜索基准统一解析临时目录物理路径，避免 macOS `/var` 与 `/private/var` 的假失败；
  重载测试比较完整 runtimepath，不再假定 netrw 必须位于三个固定路径中。

  保留装饰器及分支链的选区语义。
- 顶部栏缓存消歧后的文件名，仅生成可见范围附近的标签；长名称按显示宽度二分截断。
  名称、修改状态、只读状态仍读取实际 buffer，因此 `noautocmd` 修改也不会留下旧标签。
- Git hunk 按文件路径、changedtick、真实 index blob ID 及文本选项缓存；每次跳转仍验证

- 自动补全独立为 `completion.vim`：每批扫描约 3 ms，批次之间归还输入循环；
  默认菜单上限 100，继续输入按新前缀重新扫描。保留未保存内容、Unicode、smartcase、

## 审查修复与待继续验证项

文件树现在只判断当前标签页的窗口；重命名、删除、剪切移动检查实际返回值，移动
失败保留剪切引用。netrw 历史默认放到 `$XDG_STATE_HOME/vim-lite/netrw`，未设置时
使用 `~/.local/state/vim-lite/netrw`；已有 `g:netrw_home` 设置优先。此前插件隔离后的
runtimepath 首项是 Vim 系统目录，netrw 会尝试向那里写历史。测试也隔离安装器 HOME。

后续一轮已将复制改为后台作业。回归用延迟 300 ms 的 cp 验证调用提前返回、期间可编辑，
覆盖重复粘贴、取消保留部分文件、退出 Vim 后继续复制、目标冲突、重载及关闭原窗口。
完成时仅在原树窗口刷新；用户正在其他窗口编辑时，推迟到回到树窗口再刷新，避免大目录
刷新突然阻塞输入。`:VimTreeCopyStatus` 和 `:VimTreeCopyCancel` 提供状态与取消入口。

netrw 可选工具探测改为每个 PATH 目录只列举一次，保留原先的工具优先级、用户覆盖值、
不可读目录回退以及工具缺失时的 file:// 行为。首次打开独立测量为 114–126 ms；
与完整回归并行运行的一次测量仍达到 182 ms，不能声称冷启动已稳定低于 100 ms。

进一步审查发现：本机 netrw 的 `Lexplore 目录` 连续调用两次 `Explore`，重复遍历整个
目录。现在使用无参数的单次遍历入口，临时改变第一个窗口的局部 cwd，并在成功或异常
时恢复原目录及全局／标签页／窗口作用域；没有改动 Vim 自带插件。旧 Vim 若没有
`win_execute()`，现在通过禁止自动命令的临时窗口切换执行相同恢复逻辑。
打开目录仍实时读取；已展开子目录的缓存刷新修复见后面的兼容性记录。

1 万文件、同一基准独立启动的单次测量（无 profile，ms）：

| 场景 | 双遍历入口 | 单遍历入口 |
| --- | ---: | ---: |
| 首次打开 | 2203.21 | 1263.27 |
| 关闭后重新打开 | 2140.70 | 1086.12 |
| 刷新 | 1183.78 | 1258.08 |
| 展开一个子目录 | 134.70 | 145.46 |

后两项没有算法变更，仍受系统负载影响，不能把单样本差异解释为优化效果。性能分析
表明剩余耗时主要来自 netrw 逐文件属性读取和逐行生成树；大目录依然明显阻塞。
直接 `vim 目录` 打开 1 万文件测得约 1250 ms，包含从配置加载到 PTY 探针执行的时间，
不能与快捷键打开时间直接比较。

可选工具探测同时去掉不必要的 `fnamemodify(..., ':p')` 目录 stat，覆盖空、相对及
含空格的 PATH 条目；直接目录启动也在 netrw 自动浏览前执行同一探测。小目录重复打开
5 轮中位数约 11.85 ms，首次仍有 126.28 ms 的样本，跨挂载点读取尚未稳定低于 100 ms。
新增回归覆盖三个 cwd 作用域、非首窗口启动、特殊路径、外部新增文件、目标文件打开、
创建树窗口后异常时的目录恢复，以及直接目录启动。

后续剖析还发现，项目自身的嵌套条目路径解析会逐行寻找祖先目录；即使已经打开树，
复制路径、重命名、删除等操作仍可能因前方大量兄弟节点而停顿。现在使用原生向后搜索
匹配精确缩进深度，并恢复光标和滚动位置。没有缓存解析结果，目录展开、刷新及改名后
仍读取当前列表；回归比对原逐行算法，检查 ASCII／Unicode 混合缩进、缺失父层、
树根回退及编辑器状态，并在真实千文件子树后验证路径复制、重命名与删除。

单独构造含 10 万行展开内容的树列表，末尾条目的路径解析 3 次中位数由 629.22 ms
降至 30.60 ms（最大 31.56 ms）。此项仅测解析，不包含创建文件、netrw 列目录和屏幕重绘，
不能解释为整个文件树打开速度提升。

同时修复直接 `vim 目录` 启动后的关闭行为：原来 `<leader>e` 会另开树窗口，随后只关闭
新窗口。现在关闭当前标签页的树；唯一窗口优先切回有效的备用编辑 buffer，否则保留空窗口，
不退出 Vim、不丢掉隐藏 buffer 的修改，也不关闭其他标签页的树。1 万文件的直接启动测试
中关闭耗时 4.23 ms；该次与回归并行运行，目录启动／刷新仍为约 1.2 秒，主瓶颈未解决。

新增跨 buffer 补全 PTY 场景，实际加载 10 万个不同单词（约 1.5 MB）的另一文件后输入
`al`。原配置卡在 `Scanning: other.txt`，5 秒内没有菜单，界面计时器也不能运行；
新配置 5 轮中位数 4.57 ms、最大 4.97 ms。进一步输入窄前缀仍能找到第 10 万个词，
不会把文件候选集永久截断为最初的 100 项。自动菜单的上限是明确的行为变更，可通过
`g:vimrc_lite_completion_max` 调整；关闭菜单后 Ctrl-n/Ctrl-p 的完整扫描不受此限制。

长行分片有明确取舍：行末候选出现稍晚，但不再连续占用主线程约 77 ms。主循环间隔
包含探针读取菜单的开销，不是端到端按键时延，也不含终端网络传输。
普通密集候选另测 5 轮，中位数 4.28 ms、
最大 4.96 ms。Vimscript 字符串复制、首次取整行及菜单提交仍不能中途抢占；不承诺
任意大小的行或候选都满足 3 ms 批次预算。

继续测量正在编辑的未保存长行，而非仅把大文件放在其他 buffer。约 1 MB 的行末输入
短前缀时，原来每个补全批次都从行首匹配前缀，单次约 71 ms。现在从光标前按 4 KiB
向后寻找词首，保留 UTF-8 完整边界和跨块长前缀；由 buffer、行列、changedtick、
iskeyword 及 encoding 校验单项上下文缓存。短前缀首次提取 3 次中位数 0.35 ms，
重复检查 0.01 ms；30 万字节中文长前缀首次仍约 9.44 ms，重复检查 0.01 ms。
不截断前缀，也不关闭这类未保存 buffer 的自动补全。

剖析还发现系统 matchparen 插件在光标附近没有括号时，也通过整行正则提取当前位置，
此场景累计约 183 ms。新增 `matchparen.vim` 只做近邻配对字符预检查：没有可能的配对
字符时调用系统清理函数；有配对字符时仍使用原系统搜索、语法跳过和超时实现。
系统文件未修改；只接入识别到的辅助函数，结构不兼容时保留原插件。
光标处确实有配对字符时仍可能承担原插件的整行提取及搜索开销，该路径尚未提速。
支持 `NoMatchParen`、`DoMatchParen`、配置重载和窗口切换；SourcePost 不可用时，
手动重新启用后的系统功能仍保留，但不会自动重新接入加速。

约 1 MB 当前行的独立单次前后对照：候选到达 416.59 → 22.73 ms，主循环最大间隔
334.42 → 12.02 ms。扩大到约 10 MB 后，候选到达 262.61 ms，最大间隔 98.08 ms；
这仍明显超过 3 ms 的批次目标，不能宣称任意长行已经低延迟。计时边界与上述补全基准
相同，包含探针与编辑器事件，不是网络环境下的端到端按键时延。
新增回归逐项比对原生前缀匹配，覆盖分段边界、中文、组合字符、emoji、NUL、自定义
iskeyword、编码切换、撤销及重做；真实 PTY 验证长行前文保持完整和完整候选插入，
并与系统括号高亮逐项比较，包括插入模式、自定义配对、多窗口和开关重载。

另测约 2.2 MB、10 万行文本：清空 7.31 ms、撤销 1.92 ms、保存 13.86 ms，
去尾空白 90.83 ms，OSC 52 优化前编码 61.33 ms。后三项各测一次，磁盘及系统负载会影响结果；
另一次去尾空白达 116 ms。OSC 52 此处仅生成序列，不写终端或修改剪贴板。

单行，旧实现未能在基准的 20 秒总期限内完成；进度记录确认当时正在执行该行的清理，
不是卡在构造数据或校验结果。现在每 256 行检查字节数，平均长度达到 512 字节的块
使用原生右侧 `trim()`；其余相邻短行仍合并为一次原生替换。这样也能识别大量短行中的
单条巨型行，而不需要先复制整个 buffer 或扫描所有字符。

搜索取消的后续审查区分了两条路径：旧失败测试直接向 fzf 发送原始 Esc，绕过配置中
将 Esc 转为 Ctrl-C 的终端映射。原路径在单 CPU 受控压力下独立重复 12 次没有复现，
这不能证明之前的偶发失败已解决。新增真实 PTY 缩放后立即按 Esc 的回归覆盖文件搜索、
内容搜索、popup 和 split，合计 40 次；独立复测各组最大耗时分别为 46.51 / 46.88 /
46.30 / 46.78 ms，未保存内容、焦点、选项恢复和重复打开均通过校验。

同时复现并修复另一项取消问题：模拟能力探测忽略 SIGINT 时，原配置取消后等待 4 秒，
窗口、临时目录和作业仍存在。现在先发送 Ctrl-C，100 ms 后作业仍运行才发送 SIGTERM，
仍由既有退出／通道关闭流程收尾；该场景独立测得 107.29 ms（单次，从取消函数调用计时，
不包含外部按键解码）。回归确认探测进程没有存活，迟到的成功结果不会在取消后打开，
旧取消定时器不会终止新搜索。这里没有使用 SIGKILL，也不承诺对忽略 SIGTERM 或
不可中断 I/O 的进程提供硬性截止时间。

SIGTERM 由其退出处理接收。参见 [上游退出及历史保存实现](https://github.com/junegunn/fzf/blob/v0.62.0/src/terminal.go#L4404-L4415)
与 [信号处理](https://github.com/junegunn/fzf/blob/v0.62.0/src/terminal.go#L4171-L4184)。

### 搜索取消后的输入模式交接

Vim 8.2 的可选诊断记录显示：重开失败时终端、弹窗和作业已经清理，编辑器为普通模式，

call term_sendkeys(s:active.buf, "\<C-c>")
" 映射返回后由 Vim 执行模式切换，不插入固定等待。
return "\<C-\>\<C-n>"

### 本地树批量列举

profile 显示原生 `LocalListing()` 对普通文件反复查询类型、调用树路径转换、
检查目录，并为每项执行一次 `:put`。本轮保留原生 glob、排序、隐藏和最终树渲染，
将支持范围内的中间列举改成一次类型查询及批量追加：

```python
# 保留实际 runtime 的文件匹配、忽略规则和失效链接语义。
files = native_glob(directory)
# 每个文件查询一次类型，普通文件再检查可执行属性。
entries = [format_entry(path, getftype(path)) for path in files]
# 一次写入列表，再由原生 netrw 完成排序、隐藏与树渲染。
append_buffer(entries)
native_finish_listing()
```

仅适配 Unix 绝对本地路径、树布局、名称/扩展名排序。其他布局、大小/时间排序、
动态列宽和含换行/回车的文件名调用绑定的原函数，避免改变旧版格式或 `:put` 字符语义。
使用 `funcref()` 保留原函数对象，重定义当前进程内的入口后仍能回退，不修改系统文件。
安装适配前对完整 `LocalListing()` 函数体（去掉行号、空白行和整行注释）计算 SHA-256；
只接受已审查的 Vim 8.0.1394/v156、8.2.5172/v171、系统 Vim 9.1/v173 实现，
不因版本号相同就接受内容不同的实现。未知函数体或缺少所需 API 时不安装适配。
`g:vimrc_lite_netrw_fast_listing = 0` 随时回退；基准 `--native-listing` 使用此开关。

### 树条目类型标记与字面文件名

审查上述特殊文件名时实际复现：目录中同时有普通文件 `pair` 和 `pair@`，
选中 `pair@` 后配置的 `Entry()` 却返回 `pair`，自定义重命名/删除可能作用于错误目标。
现在树布局的解析会依据实际文件类型区分字面后缀与 `@`、`*`、`=`、`|` 标记；
若普通字面文件与带类型标记的相邻文件显示相同，或列表中的属性已过时，
拒绝猜测并返回不可操作项。真正 FIFO/socket 的标记也不再被当作物理文件名。
普通无标记条目不增加文件属性查询。

新增回归实际重命名/删除四类字面后缀文件，确认相邻无后缀文件内容不变；
另覆盖链接/可执行文件的显示冲突、列举后改变执行权限及真实 FIFO 的路径解析。
这些证据覆盖配置自定义操作的树布局路径，不外推到 netrw 原生按键、其他布局或所有
文件系统并发变更；其余路径仍需继续审查。

## 本轮修复

原来的 fp 查询与预览约 204–209 ms。仅移除 20 ms 防抖无法消除延迟。
fzf 0.62.0 修复了 [reload 后不必要的 100 ms 等待](https://github.com/junegunn/fzf/pull/4364)。
进一步仅对 fp 设置 `GOMAXPROCS=1`，合并连续输入造成的查询重启；rg 的并行扫描
和 ff/fr 的模糊匹配保持原样。初始空查询直接从空输入启动，不再运行额外 shell。
旧版 fzf 仍兼容，但本机 0.44.1 连续查询预览约 108 ms，不能通过本项严格验收。

严格检查最大值还发现退出回调本身偶发延迟约 5 秒。现在从进程创建开始每 5 ms
检查状态，确认进程已退出、终端通道已关闭才清理；不依赖回调到达后才启动检查。
回归测试同时屏蔽 exit_cb/close_cb，验证仍能打开目标文件和清理会话。
Esc 通过终端 API 直接发送取消信号，清理时唤醒旧输入循环，减少重开时的按键干扰。

当前 fzf 安装在 `/root/.local/bin/fzf`，系统 `/usr/bin/fzf` 保留。
搜索配置已安装到 `/root/.vim/`，安装器保留了原文件的 `.bak.*` 备份。

## 2026-10-04：LSP 交互与项目实例

常用导航统一使用保存原窗口、URI、位置、changedtick 和实例代数的请求。
替换、失效或超时的请求被取消；独立操作各自管理，默认超时 10 秒。
引用、实现、符号和多目标定义在列表中即时预览，确认后关闭，取消返回原位置。
单目标定义可在未保存的当前 buffer 内跳转，并保留已有 quickfix。

服务器按语言种类和规范化项目根目录分别启动，文件只发送给对应实例。
跨项目预览不创建新实例；确认目标后才正常激活。当前项目可手动启动、停止和重启，
停止状态跨文件切换和重载保留。重载更新配置，现有进程继续使用已应用的命令。

诊断默认显示 sign 和下划线，不自动弹出详情；插入模式保留原装饰，退出后刷新。
显示开关只影响当前 buffer，缓存继续用于跳转和列表；项目列表汇总同根目录的各语言。
自动单词与手动语义补全协调菜单归属，选中候选支持文档解析与缓存。
重命名准备检查、代码操作解析、字符／整行格式化及跨文件编辑整体预检均已加入。
旧版本缺少 popup 或 CompleteChanged 时界面按能力回退；本轮没有独立 Vim 8 二进制复测。
